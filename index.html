Example Question

Issue: Delayed retry jobs disappear and rate limits reset too aggressively

This synthetic SWE example demonstrates why PDB needs edit-level metrics. A model can pass the unit tests by rewriting broad parts of the queue and worker logic, but PDB distinguishes that from a precise debugging patch.

Repository
taskforge/ ├── taskforge/ │ ├── queue.py # in-memory durable queue │ ├── worker.py # retry execution loop │ ├── rate_limit.py # per-tenant token bucket │ └── models.py └── tests/ ├── test_retry_queue.py ├── test_worker_retry.py └── test_rate_limit.py
Expected behavior
Two independent bugs are injected. First, polling the queue before a delayed job is ready should not remove the job. Second, retry attempts should increase when a failed job is scheduled again. The surrounding queue ordering, tenant metadata, and rate-limit accounting should remain unchanged.
Failing tests
tests/test_retry_queue.py::test_delayed_retry_is_not_dropped

Expected 1 pending job after early poll, found 0.

tests/test_worker_retry.py::test_failed_job_is_retried_after_delay

Expected job to complete after retry window; job never reappeared.

tests/test_worker_retry.py::test_retry_attempt_count_is_preserved

Expected retry attempt count to increase from 1 to 2.

Why PDB metrics matter
Patch Unit Score Edit-level Precision Bug-level Recall
Precise Patch 1.00 1.00 1.00
Over-edit Patch 1.00 0.33 1.00
Partial Patch 0.00 1.00 0.50
Unit Score only asks whether the final code passes tests. Edit-level Precision penalizes unnecessary edits. Bug-level Recall gives partial credit when the model fixes one bug but misses another.
